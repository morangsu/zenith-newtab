> 读表注意：
> - **两个「首屏」不是一回事，不能换算**：`首屏静态链路 gzip` 是 build.mjs BUDGET_FIRST 的口径
>   （首屏必须解析的所有文件逐文件 gzip 累加）；`首帧三文件原始字节` 只是 boot.js + newtab.css +
>   newtab.html 三个阻塞文件的**未压缩**字节，不含任何 JS 模块。README 里的「xx / 70 KB」指前者。
> - 「页面 gzip 总量」把**按需模块**（点开设置 / 快照 / 轮播才下载解析）也算进去了，
>   不等于新标签页首屏实际要解析的量。
> - 「首次交互」是 0.13.0 把设置面板改成按需加载后**被转移的成本**：首屏 DOM 节点变少
>   不等于总工作量变少，必须与 rendered、DOM 节点数一起看。
> - 时间类指标受宿主机负载影响，必须用同一脚本、同一浏览器、相近时间连续采样做相对比较；
>   跨天/跨负载的绝对值不可直接比。冷启动即便多轮采样，波动仍大于热启动。

## 结论

**结构性收益是确定的**：首屏 DOM 229 → 113（−50.7%，看板节点两边都是 82，少掉的是原先首屏就构建好的设置面板）、首屏静态链路 gzip 71.9 → 68.8 KB（−4.3%）、ScriptDuration 3.58 → 3.18 ms（−11.2%）、FCP 48 → 44 ms。页面 gzip 总量 +30.9% 全部来自点开设置 / 快照 / 轮播才解析的按需模块，不进首屏链路。

**成本被转移，不是消失**：首次交互（点齿轮 → 设置面板可交互）9.2 → 17.0 ms，多了约 7.8 ms，正是按需 `import()` + 面板渲染的代价。它只在用户主动点设置时发生一次，且 17 ms 远低于可感知阈值；但只盯着「首屏 DOM 减半」就宣布「性能变好」是不完整的——这也是本轮补这个指标的原因。

**冷启动的结论被多轮采样纠正了**：0.13.0 那版报告里「冷启动 +38.9%」只有 1 个样本。这次用 9 轮全新浏览器进程 + profile 重测，0.12.0 中位数 38.1 ms、0.13.2 中位数 38.3 ms（+0.5%，范围 35.9–44.1 vs 34.2–41.9），**基本持平**；0.13.2 的 p90 还略低（44.1 → 41.9 ms）。

**热启动中位数不宜单独下结论**：本次连续采样是 22.8 → 25.4 ms（+11.4%），而上一轮同环境是 32.6 → 29.8 ms（−8.6%），p90 本次反而 −7.9%。同一个 0.12.0 基线跨负载就能从 22.8 漂到 32.6 ms，20–30 ms 量级的单次中位数差异小于噪声；判断版本优劣应以冷启动多轮、DOM/Script 这类结构性指标为准。

原始四次基准数据都保留在 `bench/{before,before2,after,after2,before3,after3}.json` 与 `bench/{before3,after3}-cold.json`，0.12.0 构建快照在 `bench/baseline-dist/chrome`，可完全复现。
